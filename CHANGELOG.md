# Changelog

## 0.3.9 — 2026-08

`transportations_library` 0.3.2 added the Chapter 20 Section 5 pedestrian mode, and nothing downstream could reach it. The vehicular TWSC surface has been bound since the beginning, but that surface is a different procedure: `WasmTwsc`'s `v13_ped` through `v16_ped` arguments carry the Section 4 pedestrian-*impedance* extension, where pedestrian volumes reduce vehicular movement capacity and the answer is still a vehicle delay. Section 5 turns that around. The pedestrian is the subject, the service measure is the proportion of pedestrians who would rate the crossing "dissatisfied" or worse, and Exhibit 20-3 sets LOS from that proportion rather than from any delay. A caller with only the vehicular binding had no way to ask the question at all.

### Added

- **`WasmPedestrianCrossing`**, the Steps 1 through 7 procedure of Exhibit 20-27 for a pedestrian crossing an uncontrolled traffic stream at a TWSC intersection or midblock. The constructor takes the whole crossing as one configuration object in the serde schema of `hcm::twsc::pedestrian::PedestrianCrossing`, and `results_to_js_value()` returns the whole `PedestrianCrossingAnalysis`, per-stage array included. This is the `WasmAlternativeIntersection` shape rather than the JSON-string shape of the PyO3 `analyze_twsc_pedestrian`. The two are the same decision seen from two sides: the core type already carries a serde schema, so the binding's job is to hand it across the boundary rather than to restate it, and on the wasm side `serde_wasm_bindgen` crosses that boundary as a JS object, so a JSON string would mean the caller serializing an object the binding immediately parses back. The inputs also do not decompose into scalars the way a lane group does. `stages` is a variable-length list whose length is the analysis structure, one entry for a crossing of the whole street and one per side of a median refuge, so a positional constructor would have to grow a stage-adding setter to say anything a two-stage crossing needs.
- **`get_stage_count()`, `get_delay()`, and `get_los()`**, the stage count as deserialized, the Equation 20-94 total pedestrian delay, and the Exhibit 20-3 LOS letter, for callers that want the headline numbers without walking the results object.
- **`WasmFreewayReliability.set_incidents()`, `clear_incidents()`, `has_incidents()`, and `incident_duration_params()`**, the Step B-7 incident inputs from a configuration object in the serde schema of the library's `IncidentInputs`, so the `incidents` object of `tests/ExampleCases/hcm/FreewayReliability/case1.json` passes verbatim. The constructor reaches incidents through exactly two scalars, the crash rate and the incident-to-crash ratio, and wraps them in an `IncidentInputs::default()`, so three inputs that change the analysis had no way in: the Equation 25-77 monthly frequencies when local incident counts are known rather than a crash rate, the Equation 25-85 severity distribution G(i), and the Exhibit 11-22 lognormal duration parameters by severity. The last of those is the whole of Chapter 25 Example Problem 9, which models improved incident management by cutting every severity's mean duration and standard deviation by 30%, so the published incident-management alternative could not be expressed through this binding at all. This is a setter taking the core's schema for the same reason `set_weather()` is one in 0.3.7, and for one more: `duration_params` is five objects of four fields each, which is not a shape a constructor argument list can carry. The two constructor arguments keep their meaning and a run that never calls the setter is bit-for-bit what 0.3.8 produced. `incident_duration_params()` reads the parameters back as the generator will use them, which is what lets a caller scale the book defaults rather than transcribe Exhibit 11-22 into its own source, and lets it confirm that the list it sent is the list that will run.

The constructor rejects a crossing with no stages instead of passing it through. `PedestrianCrossing` is `serde(default)` at both levels, so an omitted or misspelled `stages` key deserializes into a crossing of zero stages, which sums to zero delay and returns LOS A. That is the only input mistake on this surface whose result still reads like a finished answer, and it is the case a caller is most likely to hit, since every other field is a scalar whose being wrong moves a number. A dropped *second* stage is not catchable that way, because one stage is a valid crossing, which is what `get_stage_count()` is for.

## 0.3.7 — 2026-08

The last Chapter 10 input with nowhere to go on the wasm surface was the work zone. `WasmFacilitySegment` took `seg_type` through `daf` and had no way to carry one, so Example Problem 4's Segment 11 work zone was dropped on the way through the binding. That failure was silent in the worst way: the segment kept its two-lane cross section and ran at full unadjusted capacity, so the facility built, the analysis ran, and every one of the 55 cells in each of Exhibits 25-71 through 25-77 was confidently wrong. The web calculator's boundary suite had a guard pinning the tell, Segment 11 period-1 d/c reading 1.121 where the book prints 1.26, the two separated by exactly the CAF_wz of 0.892. This release closes it, and adds the segment capacity getter the same suite recorded as missing.

Chapter 11 had the same shape of problem one layer up. `WasmFreewayReliability` reached the scenario generator's demand and incident inputs but not its weather inputs, always used the Exhibit 11-18 demand ratios in place of whatever local table the analysis is built on, and passed `None` for the four facility parameters `WasmFreewayFacility` has always taken, so Example Problem 7 ran as a weather-free facility on national demand ratios at an interchange density it never specified. The Exhibit 25-104 distribution was therefore a different and milder experiment than the published one, and the calculator's boundary suite could only check it against invariants and sanity bands. This release closes those three gaps.

## 0.3.6 — 2026-08

`transportations_library` 0.3.1 corrected the two-lane facility follower density of Equation 15-39, but it did so by centralizing an aggregation that had never existed in the core, so nothing that reaches the core through this crate got the correction. Every caller was still summing the per-segment column itself. This release binds the aggregator.

It also closes the one Chapter 10 gap the web calculator's boundary suite had recorded as out of scope. The managed-lane facility of Example Problem 5 is a separate core type, not a flag on a `FreewayFacility` segment, so no combination of `WasmFacilitySegment` and `WasmFreewayFacility` arguments could express it and the six Rust tests over `ml_case1.json` had no boundary counterpart.

### Added

- **`WasmTwoLaneHighways.determine_facility_follower_density()`**, the Step 11 length-weighted facility follower density of Equation 15-39. Equation 15-39 defines FD_i as the "follower density, or adjusted follower density, for segment i", which the `fd` column of `segs_to_js_value()` does not carry on its own: a passing lane contributes FD_PLmid and a segment within the effective downstream length of an upstream passing lane contributes its Step 9 adjusted density. The web calculator's Chapter 15 page reweighted that column in JS, substituting `fd_mid` on passing lanes but taking the raw `fd` everywhere else, which drops the Step 9 benefit that most of Chapter 26 Example Problem 3 is spent computing. On that example the JS reweighting returns 8.041 followers/mi/ln and LOS D where Exhibit 26-27 publishes 7.3 and LOS C; through this method the same fixture returns 7.271 and LOS C. The binding takes `&mut self` because the core walks the segments in order to place the effective downstream length of the passing lane before the segments measured against it. That length is facility state that persists, so this binding restores the constructor's `l_de` before delegating. Without it, a caller that has already run its own per-segment `determine_adjustment_to_follower_density` loop, which is what fills the calculator's FD-adjustment column, would have left the length set, and the walk would then apply an adjustment to the segments upstream of the passing lane, whose distance from it is zero. Example Problem 4 places its passing lane fifth of six and returns 14.936 that way against 19.897; Example Problem 3 places its passing lane second and is unaffected, so the hazard hides on half the fixtures.
- **`WasmManagedLaneFacility`**, the HCM Chapter 10 managed-lane facility extension (Steps A-9/A-13/A-14/A-17, Chapter 25 Section 2). The managed lane is a parallel lane group rather than a property of a general-purpose segment, and it carries four inputs with nowhere to go on the existing surface: the per-segment ML geometry (`lane_type` from Exhibit 12-9, `lanes`, and the optional `ffs`, `caf`, `saf`, `on_ramp_demand`, `off_ramp_demand`), the ML entry demand by period, the ML facility free-flow speed, and the Step A-9 cross-weave data whose CAF of Equations 13-24/13-25 reduces the GP segment capacity before the GP analysis runs. ## 0.3.4 — 2026-08

A review of the 0.3.3 urban bindings found three ways a caller could get a wrong answer or no answer at all, and two documented claims that were not true of the code. Nothing published in 0.3.3 is removed; the constructor signature change below is invisible to JS callers passing valid input.

### Fixed

- **`WasmUrbanFacility.add_segment_from_config()` now counts a config carrying performance measures as a summary segment.** A config with any of `base_ffs_mph`, `travel_speed_mph`, `spatial_stop_rate_stops_mi`, `vc_ratio`, or `los` populated — the shape a serialized post-analysis fixture takes — used to slip past the `analyze()` guard that `add_segment_summary()` sets. `analyze()` would then run the Chapter 18 engine over the placeholder inputs sitting beside those measures and silently overwrite them. Such a segment now behaves like one added through `add_segment_summary()`: `analyze()` throws and `aggregate()` reports the supplied measures unchanged.
- **`WasmUrbanFacility.aggregate()` evaluates input-driven segments before aggregating**, which gives a facility mixing the two kinds of segment a working path for the first time. Previously `analyze()` refused the facility and directed the caller to `aggregate()`, which then failed with "base free-flow speed not computed" on the segments that had never been evaluated. Segments arriving with measures are left exactly as supplied. The `analyze()` error message now says that `aggregate()` handles the mixed case.
- **`WasmUrbanReliability`'s constructor rejects a `jan1_day_of_week` above 6** instead of clamping it to 6. The value anchors the calendar the reliability reporting period is built on, so clamping a mistaken 7 moved every Exhibit 17-6 day-of-week demand factor onto the wrong day with nothing to show for it. The Rust signature gains `Result<WasmUrbanReliability, JsValue>`, as the weaving and ramp stepwise methods did in 0.3.0 and 0.3.1; JS behavior is unchanged for values in 0 through 6.

### Corrections

- **The 0.3.3 note that snowfall "was hard-coded to zero, which silently removed the strongest weather events from the scenario stream" was wrong.** The library never reads `MonthlyWeather.total_snowfall_in`. The Chapter 29 weather procedure decides rain versus snow from the sampled temperature (Equations 29-3 and 29-4) and sizes the snow event from the precipitation columns through the snow-to-rain depth ratio of Step 7, so the snowfall column is climatological metadata that does not reach any computation. The `monthly_total_snowfall_in` argument stays, since removing a published argument would be breaking, and its doc now says it changes nothing. What actually brought the Chapter 29 Example Problem 4 wasm run onto the library's own numbers in 0.3.3 was `jan1_day_of_week`, `approach_lanes`, and `prop_left_turn_lanes`. Dropping the snowfall array from that run leaves the travel time indices bit-for-bit identical.
- **`num_oversaturated_scenarios()` was described as counting scenarios that "feed the residual queue forward".** The library's predicate flags a scenario when a boundary through movement runs over capacity (v/c > 1) or when it begins the period with a queue carried in (Q_b > 0), so the count already includes undersaturated periods inheriting a queue. The two conditions are not separable through the binding, which sees only the collapsed per-scenario flag. The doc comment now states the predicate.
