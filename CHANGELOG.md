## 0.3.13 - 2026-08

0.3.12 bound the Step A-2 segmentation and then spent a paragraph of this file warning that `segment_ramp_section`'s argument is not the gore-to-gore distance in the auxiliary-lane case. A warning is what you write when the number the caller needs is not available to them. It is available now, so the warning becomes a function.

### Added

- **`weave_influence_extension_ft()`**, the 500 ft of Exhibit 10-2, re-exported from the library the same way `ramp_influence_area_ft()` re-exports the 1,500 ft of Exhibit 10-1. A caller placing ramps by gore station passes gore-to-gore + 2 x this to `segment_ramp_section` and carries the gore-to-gore distance itself as the segment's `short_length_ft`. The reason to read it rather than write 500 down is the one the 0.3.12 notes give: the core returns the auxiliary-lane argument unchanged, so a weave coded gore-to-gore comes back well-formed and short, and a caller that has its own copy of the number is a caller whose copy can drift from the library's. The test asserts the binding reads the library's constant and then that 1,640 + 2 x 500 is what the core turns into Example Problem 1's 2,640 ft weaving segment, with the gore-to-gore coding asserted beside it at its wrong 1,640 ft, so the constant cannot be changed without the segmentation meaning failing too.

This release needs `transportations_library` 0.3.6, which exports the constant. Publish the library first.

## 0.3.12 - 2026-08

Every freeway surface this crate carries takes a facility that is already segmented. `WasmFacilitySegment` asks for a segment type and a length, and where those came from is the caller's problem. That is the right shape for a page transcribing a published example, because the example prints its own segment table, and it is the wrong shape for an editor where the user places ramps and the segments are supposed to follow. Chapter 10 Step A-2 is the missing half, and the library has had it since the Chapter 10 core landed. This release binds it, so the web calculator's facility builder derives its segment table from the library rather than from a second copy of the rules written in JS.

### Added

- **`segment_ramp_section(gore_to_gore_ft, has_auxiliary_lane)`**, the Step A-2 division of the section between an on-ramp gore and the next off-ramp gore into analysis segments, per the segmentation rules of Chapter 10 Section 2 and Exhibits 10-11 and 10-12. Returns `[{ seg_type, length_ft }]` upstream to downstream with zero-length pieces omitted, covering the four branches the core covers, which are the auxiliary-lane weave, the merge/basic/diverge series above 3,000 ft, the merge/overlap/diverge series between 1,500 and 3,000 ft, and the single truncated overlap at or below 1,500 ft that the manual calls highly unusual. The key names are the fixture schema's rather than JS-idiomatic, so a returned piece is already the head of a `FacilitySegment` and an assembling caller adds lanes and demands to it instead of translating it.
- **`ramp_influence_area_ft()`**, the 1,500 ft of Exhibit 10-1, re-exported as a function. It is here because `segment_ramp_section` describes a *pair* of ramps and an editor also has to place ramps that have no partner downstream, whose merge or diverge segment is one influence area long. That is one number, and one number written down a second time is how the two copies start to disagree.

The argument to read twice is `gore_to_gore_ft` in the auxiliary-lane case, because the core returns it unchanged as the weaving segment's length and so a wrong value arrives looking exactly like a right one. A weaving segment is not the gore-to-gore distance. Chapter 10's segmentation rules put its boundaries 500 ft upstream and 500 ft downstream of the two gores, per Exhibit 10-2, so a caller placing ramps by gore station passes gore-to-gore + 1,000 ft and carries the gore-to-gore distance itself as the segment's `short_length_ft`. Example Problem 1 settles it from the fixture side, since `tests/ExampleCases/hcm/FreewayFacilities/case1.json` gives its weaving segment a 2,640 ft length against a 1,640 ft short length, and the difference is exactly the two 500 ft extensions. The core's own doc comment names the parameter after the gore-to-gore distance in all four branches, which is accurate for three of them, and the docs added here say so at the binding rather than quietly compensating for it.

The one guard is at `gore_to_gore_ft`, and it is the crate's usual reason rather than input hygiene. The core's branch chain is a descending series of `>` comparisons, and every one of them is false against a NaN, so a NaN spacing falls through to the final arm and comes back as one well-formed `OverlappingRamp` piece of NaN length. That length then survives `FreewayFacility::validate`, whose test is `length_ft <= 0.0` and is therefore also false against it, so the facility built on it analyzes and prints numbers rather than failing. A NaN reaches a builder from an emptied number input as easily as from arithmetic. The spacing must be finite and positive, and the test that pins this asserts what the core returns without the guard, including that the NaN passes the validator's literal expression, with a control showing the 2,000 ft section still segments into merge 500 / overlap 1,000 / diverge 500.

Neither function needs the library to move, so `transportations_library` stays at 0.3.5 and this release publishes alone.

## 0.3.11 - 2026-08

Chapter 14 answers one question, and Chapter 28 Example Problem 5 asks the other one. The whole surface this crate has carried for merges and diverges runs the analysis forward, from a demand to a density to a level of service, which is the question a caller asks about a junction that exists. Example Problem 5 asks what demand a junction can carry before it drops out of a given LOS, and that is not the same computation run backwards, because Equation 14-22's density depends on the demand through the lane-distribution model as well as directly. The library answers it by searching, and until now the search was reachable from Rust and Python but not from JS, so the web calculator's boundary suite covered Example Problem 5 by feeding the book's own published answers back in as demands and checking the densities that came out. That reaches the published numbers and not the procedure that produces them, and it cannot reach the prevailing-condition columns of Exhibits 28-4 and 28-5 at all.

### Added

- **`ramp_service_flow_rate_ideal(template, basis, target_density)`**, the Chapter 28 Example Problem 5 search for the service flow rate under equivalent ideal conditions at a target ramp-influence density. `template` is a borrowed `WasmRampSegment` rather than a consumed one, so one handle answers a whole LOS column; the core clones it per probe and substitutes PHF = 1, no heavy vehicles and CAF = SAF = 1, so the template contributes its geometry and nothing else. Returns `undefined` when the target density is already exceeded at zero varied demand, which is how the book reports an unachievable LOS rather than an error, and note that `serde_wasm_bindgen` crosses `None` as `undefined` and not `null`.
- **`ramp_service_volumes(sfi, f_hv, f_p, phf)`**, the conversion to the prevailing-condition service flow rate and service volume, returning `{ sf, sv }` in veh/h. Named rather than a pair because SF and SV differ only by the PHF, so a transposed pair reads as a finished answer.
- **`ServiceDemandBasis` crossing as its serde form**, an object carrying the variant name as its single key: `{"ApproachingFreeway": {"ramp_fraction": 0.10}}` for Case 1, where the ramp tracks the freeway and the returned quantity is v_F, and `{"FixedFreeway": {"v_f": 4896.0}}` for Case 2, where the freeway is held and the returned quantity is v_R. This is the route `AtdmStrategy` already takes, and it is the right one here for a reason particular to this enum: both variants carry exactly one required `f64` with no serde default, so a misspelled inner field is rejected as a missing field rather than dropped, and a basis carrying both variant keys at once is rejected as ambiguous rather than resolved by key order. What no schema can catch is a caller sending the basis it did not mean, since both return a plausible flow and only the label on it changes, so the two are documented as the different questions they are.

Both free functions are bound in the shape `edtt_merge` and `stop_junction_delay` established in 0.3.2, not as methods on `WasmRampSegment`, because that is what they are in the core and because the template is an input to the search rather than the thing being analyzed.

The one guard this release adds is at the search inputs, and it is worth saying what it is for, because the crate's other guards exist for configurations that arrive wrong and still produce a finished answer, and this is one of those. The core searches by comparing densities, and every comparison against a NaN is false, so a non-finite `target_density` or basis parameter walks straight through the search's own escape hatches: the "already past the target" test does not fire, so the unachievable-LOS `None` is not returned, the bracket never doubles, and the bisection drives its upper bound to zero. What comes back is `Some(4.4e-13)`, a service flow rate of zero rather than a failure, on a segment whose real LOS C answer is above 5,000 pc/h. A NaN arrives from an emptied number input as readily as from arithmetic, so `target_density` must be finite and positive and the basis parameter finite and non-negative, and the rejection names the field, since each variant carries only one number and "invalid" would not tell a caller which basis it sent. Two host-side tests pin it, and the first asserts what the core returns without the guard rather than only that the guard fires, with a control showing the same search still finds the published LOS C value.

What was checked rather than assumed, through a web-target pkg driven from node. Example Problem 5 reproduces through the binding what `chapter14_integration.rs` asserts in the core, and then some, since the Rust test pins three of the twelve prevailing-condition cells and the boundary now pins all twelve. It stands in the web calculator's boundary suite as the second half of `tests/boundary/ch14_merge_diverge.mjs`, taking that file from 75 checks to 117. Case 1 solves v_F at the Exhibit 14-3 thresholds and returns 1,978.23, 3,810.77 and 5,276.81 pc/h against a published 1,979, 3,813 and 5,280, giving SF 1,857.49, 3,578.19 and 4,954.75 against 1,858, 3,580 and 4,958 and SV 1,616.02, 3,113.02 and 4,310.63 against 1,616, 3,115 and 4,313, with the capacity-limited LOS E row at 6,545.45, 6,145.97 and 5,346.99 against 6,545, 6,146 and 5,347. Case 2 returns SFI 772.35 and 1,726.03, SF 725.21 and 1,620.69, SV 630.94 and 1,410.00 against a published 772/725/631 and 1,726/1,621/1,410, and at LOS E 2,000, 1,877.93 and 1,633.80 against 2,000, 1,878 and 1,633.

Both of the book's NA determinations come through as the book states them rather than as something standing in for them. Exhibit 28-5's LOS A and B return the absence itself, since the density at 4,896 pc/h and zero ramp flow is already 22.33 pc/mi/ln. Exhibit 28-4's LOS D is the other kind: the solver does find the flow that reaches density 35, at 6,559.6 pc/h, and it exceeds the LOS E capacity flow of 6,545.5, which is the book's statement that capacity is reached before the density threshold is.

Exhibit 28-5 disagrees with itself, and this release settles it a second time from the opposite direction. Its SFI column prints 769 and 1,723 for LOS C and D while the SF column beside it multiplies 772 and 1,726 by 0.939. The solved values sit 0.35 and 0.03 pc/h from the arithmetic basis and 3.35 and 3.03 from the printed column. The core's test already took 772 and 1,726 and the calculator's forward block agreed on densities; the search agrees on flows.

The tolerances the boundary uses on the SF and SV columns are not the core's flat +-3 veh/h and the difference is deliberate. The book computed each SF from its own rounded SFI, so the flow tolerance is carried through the same two multiplications the columns are, giving +-5.63 and +-4.90 veh/h on Case 1 and +-2.82 and +-2.45 on Case 2. Case 2's derived bands are tighter than the flat +-3, so this is not a widening in disguise; the one cell that needs the Case 1 band is LOS C's SF, whose 3.25 veh/h residual is the book's rounded 5,280 carried through 0.939.

Three checks say the template is read and read correctly, since a search that ignored its template would still return a number. One handle answers repeated probes with identical results, which is what the borrow buys. A template built with a real peak hour (9,999 pc/h freeway demand, 8,888 ramp, PHF 0.5, 30% trucks) returns the identical LOS C flow, so the ideal-conditions substitution is happening. And shortening the acceleration lane from 1,000 ft to 300 ft moves that flow from 5,276.8 to 4,601.4 pc/h, so the geometry is not being ignored either.

`transportations_library` stays at 0.3.5, which is already on crates.io, so unlike the 0.3.10 line this release publishes alone.

## 0.3.10 — 2026-08

`transportations_library` 0.3.5 implemented the HCM Chapter 25/26 mixed-flow model, and this release binds it. Every freeway surface this crate has carried until now runs the Chapter 12 passenger-car-equivalent method, which converts trucks into passenger cars and then analyses one homogeneous stream. That stops describing anything real on a sustained steep grade, where the trucks are not slowed automobiles but a separate population settling towards a crawl speed the automobiles never approach. The two methods are meant to disagree, and Chapter 26 Example Problem 5 exists to show by how much: the same 2 mi 5% upgrade comes out at 25.2 veh/mi/ln through the PCE path and 31.7 through this one.

### Added

- **`WasmMixedFlow`**, the Chapter 26 Steps 2 through 8 chain for a single grade (Equations 26-1 through 26-22). The constructor takes the whole segment as one configuration object in the serde schema of `hcm::basicfreeways::mixed_flow::MixedFlowSegment`, so the library's own `tests/ExampleCases/hcm/Chapter26/ep5_mixed_flow.json` passes verbatim, and `results_to_js_value()` returns the whole `MixedFlowResult`. This is the `WasmPedestrianCrossing` shape rather than the JSON-string shape of the PyO3 `analyze_mixed_flow`, for the reason 0.3.9 gives: the core type already carries a serde schema, `serde_wasm_bindgen` crosses it as a JS object, and a JSON string would mean the caller serializing an object the binding immediately parses back.
- **`WasmCompositeGrade`**, the Chapter 25 chain over consecutive grades (Equations 25-53 through 25-70), taking `hcm::basicfreeways::composite_grade::CompositeGrade` the same way, so `tests/ExampleCases/hcm/Chapter25/ep11_composite_grade.json` passes verbatim. `segments` is in the order a vehicle meets the grades and the order is an input rather than a presentation detail. What Chapter 25 adds over Chapter 26 is that a truck enters each grade at the speed the grade above it left it at, so reversing the three grades of Example Problem 11 puts the 5% first and walks the trucks off the digitised curves entirely.
- **`get_capacity_mix()` and `get_density()` on `WasmMixedFlow`, and `get_segment_count()`, `get_capacity_mix()` and `get_overall_speed()` on `WasmCompositeGrade`**, for callers that want the headline numbers without walking the results object. `get_segment_count()` is the readback rather than a convenience: a composite grade that arrives one segment short is a valid facility that analyzes and prints a number, so it is the one input mistake on this surface no validation can catch.

Both `results_to_js_value()` methods return a `Result` rather than a bare `JsValue`, which is the difference between this surface and every other config-object binding in the crate. The truck-performance curves the method reads are published as figures with no closed form anywhere in either chapter, so the library digitises them from the exhibit rasters, and only for the grades and speeds the two published worked examples need. A configuration can be entirely well-formed and still land outside them, which is a refusal about coverage rather than about the configuration, so it belongs at the analysis rather than at the constructor. Each refusal names the exhibit that would have to be digitised. Asking for the Example Problem 5 segment at FFS 70 instead of 65 throws "no Stage-1 travel time curve for Sut at 70 mi/h FFS, 5% grade; the Chapter 26 Appendix A exhibit for that combination has not been digitised", and putting a 7% grade into Example Problem 11 throws "grade 7% is not digitised in Stage 1 of the mixed-flow truck curves (available: -5, 0, 2, 3, 5); Exhibit 25-20/25-21 would have to be digitised for it". The alternative is extrapolating between curves whose crawl speed is grade-specific, which would be quietly wrong rather than approximately right. `analysis_error` is a plain string function precisely so this crate's host-side tests can assert that the wrapper prefixes the core message rather than replacing it, since a `JsValue` cannot be constructed off-target; that is what the two refusal tests in `wasm_mixed_flow.rs` check.

Neither constructor adds validation of its own, which is worth stating because the rest of this crate's config-object bindings do, and because the 0.3.7 and 0.3.9 notes explain at length why they do. The condition those guards exist for is an input that arrives wrong and still produces a finished answer, and this surface has none. `caf_ao` is the only serde-defaulted field on either type, and its default of 1.0 is the no-adjustment case rather than a stand-in for something the caller meant to supply; every other field is required, and since library 0.3.5 both input structs deny unknown keys, so any misspelled key — including a typo'd `caf_ao`, which would previously have been dropped in favor of the 1.0 default — is rejected naming the key. `segments` has no default either, and an explicitly empty list is rejected by the core's own `validate` before it reaches the per-segment capacity minimum that would panic on it. That ordering is load-bearing, since a panic in wasm aborts the module rather than throwing something catchable, so a test in this crate pins it and says that if the check ever moves behind the minimum the guard belongs back in the constructor.

The unit conventions are the manual's and they mix within a single object, which is the one thing a caller building these configs by hand should read twice. `length` is in MILES, not the feet a Chapter 15 subsegment takes. `grade` is in PERCENT. `p_sut` and `p_tt` are DECIMALS, the opposite convention from `grade` beside them. Two of the three mistakes are caught: a percent in `p_sut` fails because the proportions must sum below one, and a decimal in `grade` fails because 0.05 is not one of the digitised grades. A length in feet is not caught, because a grade has no upper length to check against.

What was checked rather than assumed, through a web-target pkg driven from node against the library's own fixtures loaded verbatim. Both worked examples reproduce through the binding what the core's `chapter12_integration.rs` and `chapter25_composite_grade_integration.rs` assert, at the same tolerances, in 86 checks now standing in the web calculator's boundary suite as `tests/boundary/ch25_26_mixed_flow.mjs`. Chapter 26 Example Problem 5 returns CAF_T,mix 0.1352, CAF_g,mix 0.1302 and CAF_mix 0.7345 against published 0.135, 0.131 and 0.734, C_mix 1,726.2 veh/h/ln against a published 1,725 (the example carries CAF_mix rounded to three decimals into Equation 26-5, which is the whole of that gap), kinematic truck rates 71.37 and 92.12 s/mi against 71.1 and 92.2, FFS_mix 60.139 against 60.1, BP_mix exactly 0, calibration speeds 37.53 and 44.38 against 37.5 and 44.3, phi 4.097 against 4.07, S_mix 47.42 against 47.3, and D_mix 31.63 against 31.7. Chapter 25 Example Problem 11 returns per-segment capacities 1,874.5 / 1,932.8 / 1,747.5 veh/h/ln against published 1,875 / 1,934 / 1,746 with the 1 mi 5% grade governing, segment speeds 57.69 / 58.77 / 48.12 mi/h against 57.7 / 58.7 / 47.9, travel times summing to 290.93 s, an overall 55.68 mi/h against a published 55.6, and the Exhibit 25-109, 25-110 and 25-111 speed triples for automobiles, SUTs and TTs.

Three of the values above are not the ones printed in the manual, and the self-consistent one is asserted in each case, as in the core. Example Problem 5's Step 8 computes a density of 31.7 veh/mi/ln and a comparison paragraph a few lines later quotes 32.6, which no step produces and which would need a mixed-flow speed of 46.0 mi/h. Example Problem 11's Segment 2 Step 6 prints `tau_mix,2 = 62.6 s/mi` and then divides 3,600 by 61.3 on the next line, and 61.3 is what its own Step 5 rates give and what the published segment travel time and Exhibits 25-110 and 25-111 agree with. Step 7's prose says the segment travel times "equal 294 s" where they sum to 291.5, which is what Equation 25-70 divides into to reach the published 55.6. Equation 26-16 is a fourth case and is treated differently: it is implemented as printed, `max[0, e^(30g) + 1]`, even though the `+ 1` is almost certainly a typo for `- 1`, because the printed form drives BP_mix to zero here and the example then rationalises that zero in words rather than treating it as an error, and because BP_mix feeds Equations 26-20 and 26-21, so correcting the sign would silently move the published speed and density.

Two things this release does not do. The chaining that distinguishes Chapter 25 from Chapter 26 is invisible in the published numbers, so it is pinned by a comparison rather than by a value: the 2% middle grade of Example Problem 11 comes out slower when entered by trucks the 3% grade above it has already slowed than it does analysed alone, and if the chaining were ever dropped the two would agree and every published number would merely drift a little. And the oversaturated case is worth reading before rendering anything from this surface. Above mixed-flow capacity Chapter 26 Step 2 stops at LOS F rather than reporting a speed, so `s_mix` and `d_mix` are `None`, and `serde_wasm_bindgen` crosses a `None` as `undefined` rather than as `null`. A consumer testing `s_mix === null` before rendering would print the oversaturated case as a speed.

HCM-coverage releases stay within the 0.3.x family so the CrossTraffic crates carry a matched version line. `transportations_library` 0.3.5 is not on crates.io yet, so the library publishes first; the `Cargo.toml` dependency carries that note.

## 0.3.9 — 2026-08

`transportations_library` 0.3.2 added the Chapter 20 Section 5 pedestrian mode, and nothing downstream could reach it. The vehicular TWSC surface has been bound since the beginning, but that surface is a different procedure: `WasmTwsc`'s `v13_ped` through `v16_ped` arguments carry the Section 4 pedestrian-*impedance* extension, where pedestrian volumes reduce vehicular movement capacity and the answer is still a vehicle delay. Section 5 turns that around. The pedestrian is the subject, the service measure is the proportion of pedestrians who would rate the crossing "dissatisfied" or worse, and Exhibit 20-3 sets LOS from that proportion rather than from any delay. A caller with only the vehicular binding had no way to ask the question at all.

### Added

- **`WasmPedestrianCrossing`**, the Steps 1 through 7 procedure of Exhibit 20-27 for a pedestrian crossing an uncontrolled traffic stream at a TWSC intersection or midblock. The constructor takes the whole crossing as one configuration object in the serde schema of `hcm::twsc::pedestrian::PedestrianCrossing`, and `results_to_js_value()` returns the whole `PedestrianCrossingAnalysis`, per-stage array included. This is the `WasmAlternativeIntersection` shape rather than the JSON-string shape of the PyO3 `analyze_twsc_pedestrian`. The two are the same decision seen from two sides: the core type already carries a serde schema, so the binding's job is to hand it across the boundary rather than to restate it, and on the wasm side `serde_wasm_bindgen` crosses that boundary as a JS object, so a JSON string would mean the caller serializing an object the binding immediately parses back. The inputs also do not decompose into scalars the way a lane group does. `stages` is a variable-length list whose length is the analysis structure, one entry for a crossing of the whole street and one per side of a median refuge, so a positional constructor would have to grow a stage-adding setter to say anything a two-stage crossing needs.
- **`get_stage_count()`, `get_delay()`, and `get_los()`**, the stage count as deserialized, the Equation 20-94 total pedestrian delay, and the Exhibit 20-3 LOS letter, for callers that want the headline numbers without walking the results object.
- **`WasmFreewayReliability.set_incidents()`, `clear_incidents()`, `has_incidents()`, and `incident_duration_params()`**, the Step B-7 incident inputs from a configuration object in the serde schema of the library's `IncidentInputs`, so the `incidents` object of `tests/ExampleCases/hcm/FreewayReliability/case1.json` passes verbatim. The constructor reaches incidents through exactly two scalars, the crash rate and the incident-to-crash ratio, and wraps them in an `IncidentInputs::default()`, so three inputs that change the analysis had no way in: the Equation 25-77 monthly frequencies when local incident counts are known rather than a crash rate, the Equation 25-85 severity distribution G(i), and the Exhibit 11-22 lognormal duration parameters by severity. The last of those is the whole of Chapter 25 Example Problem 9, which models improved incident management by cutting every severity's mean duration and standard deviation by 30%, so the published incident-management alternative could not be expressed through this binding at all. This is a setter taking the core's schema for the same reason `set_weather()` is one in 0.3.7, and for one more: `duration_params` is five objects of four fields each, which is not a shape a constructor argument list can carry. The two constructor arguments keep their meaning and a run that never calls the setter is bit-for-bit what 0.3.8 produced. `incident_duration_params()` reads the parameters back as the generator will use them, which is what lets a caller scale the book defaults rather than transcribe Exhibit 11-22 into its own source, and lets it confirm that the list it sent is the list that will run.

The constructor rejects a crossing with no stages instead of passing it through. `PedestrianCrossing` is `serde(default)` at both levels, so an omitted or misspelled `stages` key deserializes into a crossing of zero stages, which sums to zero delay and returns LOS A. That is the only input mistake on this surface whose result still reads like a finished answer, and it is the case a caller is most likely to hit, since every other field is a scalar whose being wrong moves a number. A dropped *second* stage is not catchable that way, because one stage is a valid crossing, which is what `get_stage_count()` is for.

What was checked rather than assumed, through a nodejs pkg against the library's own `tests/ExampleCases/hcm/Twsc/case4_pedestrian.json` loaded verbatim. All three scenarios of Chapter 32, TWSC Example Problem 2 reproduce through the binding what `chapter20_integration.rs` asserts in the core, at the same tolerances. Scenario A, the 46-ft unmarked single-stage crossing of four lanes at a 0% yield rate, returns t_c 12.5 s, P_b 0.771, P_d 0.997, d_g 760.55 s against a published 761, d_gd 762.64 against 763, every P(Y_i) exactly zero, a total delay of 760.55 s, O(S/D) 1.0665 and 0.1588 against 1.066 and 0.159, P_nd 0.0027 against 0.003, P_D 0.862, and LOS F. Scenario B, two 20-ft stages behind a marked crosswalk and median refuge at 50% yield, returns t_c 6.0 s, P_b 0.508, P_d 0.757, d_g 7.23 s, d_gd 9.54 s, h 2.31 s, n = 4, the book's three running cumulative P(Y_i) sums at 0.314, 0.498, and 0.606, 2.98 s per stage and 5.96 s in total against a published 3.0 and 6.0, and the Exhibit 32-7 row at O(S/D) 13.43 and 2.00, P_nd 0.481, P_D 0.206, LOS C. - **`WasmUrbanReliability`'s constructor rejects a `jan1_day_of_week` above 6** instead of clamping it to 6. The value anchors the calendar the reliability reporting period is built on, so clamping a mistaken 7 moved every Exhibit 17-6 day-of-week demand factor onto the wrong day with nothing to show for it. The Rust signature gains `Result<WasmUrbanReliability, JsValue>`, as the weaving and ramp stepwise methods did in 0.3.0 and 0.3.1; JS behavior is unchanged for values in 0 through 6.

### Corrections

- **The 0.3.3 note that snowfall "was hard-coded to zero, which silently removed the strongest weather events from the scenario stream" was wrong.** The library never reads `MonthlyWeather.total_snowfall_in`. The Chapter 29 weather procedure decides rain versus snow from the sampled temperature (Equations 29-3 and 29-4) and sizes the snow event from the precipitation columns through the snow-to-rain depth ratio of Step 7, so the snowfall column is climatological metadata that does not reach any computation. The `monthly_total_snowfall_in` argument stays, since removing a published argument would be breaking, and its doc now says it changes nothing. What actually brought the Chapter 29 Example Problem 4 wasm run onto the library's own numbers in 0.3.3 was `jan1_day_of_week`, `approach_lanes`, and `prop_left_turn_lanes`. Dropping the snowfall array from that run leaves the travel time indices bit-for-bit identical.
- **`num_oversaturated_scenarios()` was described as counting scenarios that "feed the residual queue forward".** The library's predicate flags a scenario when a boundary through movement runs over capacity (v/c > 1) or when it begins the period with a queue carried in (Q_b > 0), so the count already includes undersaturated periods inheriting a queue. The two conditions are not separable through the binding, which sees only the collapsed per-scenario flag. The doc comment now states the predicate.
